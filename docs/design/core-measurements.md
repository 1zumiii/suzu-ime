# 推理核心重构：测量报告

本文记录新核心与旧核心的对照测量，对应需求文档第 4 节的验收指标。设计取舍见 [core-design.md](core-design.md)。原始数据在 `docs/design/data/`。

全部数据来自同一台 Linux 云主机（4 个 vCPU，15 GB 内存），没有手机、Mac 与 Windows 机器。手机上的数值须在真机上重测，本文给出的是代理指标。

## 1. 方法

### 1.1 按键仿真

`tests/keysim.lua` 用模拟的 Rime 环境驱动真实的处理器、过滤器与核心，调用方式与线上一致。打字节奏：

- 按键间隔 100～300 ms，其中 15% 为 40～80 ms 的快速连按；
- 输入中途 8% 的概率退格改字；
- 上屏后 10% 输入标点，8% 退格（清上文），5% 回车（清上文）；
- 15% 的词为四字（触发第二阶段）；10% 的词之后停顿 0.5～2 秒。

上文与候选取自留出集的 1293 题。每次运行 100 个词，约 950 次按键、250 次打分请求。

统计口径：

- 跳过率 = 上文至少 2 个字、候选至少 2 个的第一阶段请求中，没有拿到结果的比例。上文不足 2 个字的请求核心本来就不打分，单列为“不合格”，不计入跳过。
- score 等待：每次 `score` 调用的墙钟时间，守护进程模式含进程间通信。
- 按键耗时：一次按键里处理器与过滤器的总墙钟时间，即输入法线程实际被占用的时间。

### 1.2 降速注入

“2.5 倍”表示每次解码完成后再等待解码耗时的 1.5 倍，等待期间工作线程照样被占用，排队与超时的结构与真慢的设备一致。新核心用构建选项 `SUZU_TEST_HOOKS`，旧核心用链接时包装 `llama_decode` 的同一方法。2.5 倍下旧核心的打分中位数约 34 ms，与手机实测的“未命中约 30 ms”同量级，用作手机的代理。

### 1.3 重复与对照

新旧核心、进程内与守护进程、1 倍与 2.5 倍降速，共 8 个配置。交替运行 3 轮，同一轮的 8 个配置用同一随机种子，即同一段打字脚本。表中给出 3 轮的中位数，括号内为最小～最大。线程数均为 2（与手机一致）。复现方法：

```bash
tools/keysim_matrix.sh -n 100 -r 3 -s "1 2.5" -o out.txt <suzu.gguf> <suzu.vocab.txt> new=<新核心构建目录> legacy=<旧核心构建目录>
python3 -I tools/keysim_summary.py out.txt --markdown
```

要点：

- 打分中位数，新核心约为旧核心的 57%（1 倍：13.5 ms → 8.0 ms；2.5 倍：33.7 ms → 18.8 ms）。
- 尾部有上限：新核心的 score 最大值不超过时限（30、40、45 ms），按键最大值的余量来自第二阶段（时限 70 ms）。旧核心没有时限，2.5 倍降速下守护进程模式的按键最大值为 116 ms（3 轮中最大 134 ms）。
- 代价是降速下少量的超时跳过：超时的请求结果进缓存，下一次按键直接用上。手机代理条件（守护进程，2.5 倍）下为 1.1%，低于 2% 的目标。
- 1 倍下两种核心都没有真跳过。旧核心统计里的“跳过”全部来自上文不足 2 个字的请求，见设计说明 1.1 节。每轮 70～89 次，占全部打分请求的 25%～34%。

### 2.1 超时出在哪里

2.5 倍降速、时限 30 ms 的一次运行中，7 次超时的上文全部完全命中缓存，时间花在一次 2～5 个字的候选解码上，降速前约 12～23 ms，而通常只要 4 ms。用推理层基准复现：每题打分前空闲 150 ms 时，候选解码的中位数由 3.7 ms 变为 7.2 ms，p99 为 14 ms。这是空闲后的冷启动（缓存与 CPU 状态），与线程池无关：常驻线程池（自旋 0）、常驻线程池（自旋 50）与每次临时建线程的结果相同，自旋 50 还出现过一次 116 ms。手机在按键之间降频，同样的现象可能更明显，这也是“有时突然卡一下”的一个可能来源，须在真机上确认。

| 只缺 KV 共享 | 12.62 | 24.84 | 93.60 | 7.52 | 2.95 |

| 新核心与旧核心（Linux） | 1293/1293 | 1293/1293 | 0.0000 |
| 新核心与基准文件 `res_q8.tsv` | 1293/1293 | | |

首选准确率（首选等于标准答案）三者均为 92.42%。旧核心与基准文件的完整排序有 9 题不同，来自不同机器上的浮点误差，不影响首选。

## 8. 局限

- 降速注入只拉长解码，不模拟手机的大小核调度、降频与息屏，2.5 倍只是量级上的代理。
- 仿真的上文来自留出集的句子，与真实输入的上文长度分布不同；跳过构成的比例因此与手机不同。
- 每个配置只有 3 轮，100 个词一轮；几毫秒的中位数差别不作为判断依据。
- 进程间通信走本机回环，手机上 Trime 与守护进程之间的通信开销（旧测量约 4～6 ms）没有体现。
