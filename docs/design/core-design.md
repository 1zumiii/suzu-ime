# 推理核心重构：设计说明

本文说明新核心（`core/`）采用了哪些做法、舍弃了哪些、依据是什么。测量数据见 [core-measurements.md](core-measurements.md)，接口与构建见 [core/README.md](../../core/README.md)。

文中的证据强度分三档：实测（本仓库的 Linux 环境，4 个 vCPU）、代码阅读、推测。手机与 Mac 的实测数据见仓库根目录的 README.md，第 6 节列出各项的验证状态。

## 1. 旧核心问题的调查结果

### 1.1 19% 的跳过里有什么

结论：旧守护进程的 `skipped` 计数里，绝大部分不是“没赶上”或“被占锁”，而是上文不足 2 个字、核心本来就不打分的请求。这一点由代码阅读与仿真得出，尚待真机确认。

代码阅读的依据有三条：

- 旧守护进程 `call_score` 只要引擎返回的不是表就计一次 `skipped`。引擎在上文不足 2 个字时返回不带原因的 `nil`，也被计入。
- 学生模式的打分走 `score_student_locked`，它不检查 `allow_sync`，上文没预解码就现场解码。因此学生模式下 `skip_unprepared` 恒为 0。
- `skip_busy` 只在后台预解码持锁超过 30 ms 时出现。Suzu 解码一整段上文在手机上约 12 ms，很少达到。

处理器在退格、回车、方向键之后清空上文，标点上屏后上文也常常只有一两个字。这之后的每次打分请求都属于这一类。

仿真结果（`tests/keysim.lua`，旧核心、守护进程模式，120 个词）：守护进程报 `skipped` 84 次，占全部打分请求的 25%，`skip_unprepared` 与 `skip_busy` 均为 0。这 84 次全部是上文不足 2 个字的请求；上文合格的请求 218 次，全部拿到了结果。手机实测的 157 /（683 + 157）= 18.7% 与这个构成相符，比例的差别来自编辑键的频率。

新核心把这类请求单列为 `no_context`，`skipped` 只统计真正的跳过（时限内没算完、模型未就绪、出错、连不上）。真机上对比这两个字段，即可确认上述判断。

### 1.2 偶发卡顿从哪里来

逐个候选原因的结论如下。

| 候选原因 | 结论 | 证据 |
|---|---|---|
| 推理线程数等于核数 | 是毛刺的主要来源之一。任何一个线程被抢占，整批解码就停下来等它。4 个 vCPU 上开 4 线程，同一组题的最大值为 50～90 ms；开 2～3 线程，最大值为 22～39 ms | 实测 |
| llama.cpp 每次解码临时创建线程 | 不给线程池时，ggml 每次计算都新建并回收线程。改为常驻线程池后中位数略降，毛刺主要仍取决于线程数 | 实测、代码阅读 |
| 打分忙等预解码的锁 | 旧核心最多忙等 30 ms，期间占用输入法线程 | 代码阅读 |
| 第二阶段现场解码 | 旧客户端给第二阶段的时限是 600 ms；第二阶段的上文还会覆盖已预解码的第一阶段上文，下一次按键须整段重解 | 代码阅读 |
| 守护进程重启后的重连 | 旧客户端的一次调用最多叠加连接 40 ms、认证 150 ms、每项配置 150 ms 与请求本身的时限，合计可超过 300 ms | 代码阅读；新客户端在故障注入下实测最大 50.7 ms |
| 预解码请求在输入法线程上同步等待 | 旧客户端的 `prepare` 时限 100 ms，守护进程的连接线程若正忙，请求要排在后面 | 代码阅读 |
| 息屏降频、Lua 垃圾回收 | 无法在本环境复现 | 未验证 |

“守护进程内部最大一次 105 ms”与上表的前两项和第二阶段现场解码都对得上，具体是哪一项，须在真机上看新核心状态里的分项计时（排队、计算、等待）才能确定。

## 2. 架构

```
输入法线程（Lua）
   │ score / prepare / is_ready …            ← lua/（进程内）或 client/（守护进程模式）
   ▼
runtime::Engine ── 队列（微秒级的锁）──▶ 工作线程 ──▶ model::SuzuModel ──▶ llama.cpp
   │ 结果缓存、统计                                     上文缓存、前缀树
```

### 2.1 模型只归工作线程所有

模型只在工作线程上创建、使用和释放，调用方从不碰它。旧核心的模型锁、生命周期读写锁、加载标志、挂起请求槽位与忙等都不再需要。Engine 的锁只保护队列与状态，持锁时间是微秒级，工作线程计算时不持锁。

空闲卸载由工作线程自己计时完成，与旧核心的属性 `idle_unload_sec` 兼容。卸载与使用不可能同时发生，因此旧核心为此做的竞态加固都不再需要。

### 2.2 每个调用都有上限

调用方只做三件事：查结果缓存、提交任务、在时限内等待。

- `score`：第一阶段默认 40 ms（守护进程 45 ms），第二阶段默认 70 ms（守护进程 70 ms）。2.5 倍降速下，进程内时限 30 ms 时跳过率为 3.4%，40 ms 时为 0.6%（见测量报告）。
- 超时的任务继续算完，结果进缓存。过滤器在跳过后的下一次按键会用同样的上文与候选再问一次，直接命中缓存。
- 等待方已放弃、且后面还有新请求的任务直接丢弃，不占用工作线程。
- `prepare`、`is_ready`、`touch`、`status` 立即返回。

这样，旧核心的“未预解码即跳过”（`allow_sync = false`）就变成了“在时限内现场解码”。Suzu 解码一整段上文只要几毫秒，时限内几乎总能算完。

### 2.3 守护进程不再内嵌 Lua

旧守护进程内嵌两个私有 Lua 状态，经 Lua 调用引擎。新守护进程直接调用 Engine，连接线程从不自己算。守护进程保证在时限内应答，超时就应答 `N timeout`，连接上不会残留迟到的应答，所以不需要请求编号。客户端只有在守护进程整个无响应时才会用满自己的时限，这时断开重连。

客户端的每次调用有总时限，连接、认证、重发配置都算在里面。连不上时立即返回，并按 0.5 秒到 10 秒指数退避。

## 3. 采用的做法

| 做法 | 依据 | 效果 |
|---|---|---|
| KV 缓存共享存储（`kv_unified`） | 旧核心每条候选序列独占一段 KV，序列复制要搬数据 | 候选解码中位数 8.4 ms 降到 2.9 ms（4 线程，留出集全集，实测） |
| 首字相同的候选共享解码（前缀树） | 重构前的推算 | 候选部分送进模型的字数平均 3.74 降到 2.95（减少 21%）；耗时只降约 0.5 ms，因为小批量解码的耗时主要由权重读取决定（实测） |
| 上文缓存两条，按共享前缀增量解码 | 第二阶段的上文不再覆盖第一阶段的上文；上屏后新上文在旧上文后面追加时只解码新增的字 | 仿真中打分时上文完全命中 216 次、部分命中 12 次、整段重解 0 次（实测） |
| 结果缓存（64 条） | 翻页、候选窗重建与超时后的再次请求 | 超时后的下一次按键直接拿到结果 |
| 常驻线程池，自旋程度 0 | 避免每次解码临时建线程；做完立即睡眠，不空耗电量 | 中位数约降 0.5 ms，毛刺不变（实测）；耗电未测 |
| 线程数不超过核数减一 | 1.2 节的第一项 | 4 vCPU 上 4 线程时最大值 50～90 ms，3 线程时 22～39 ms（实测） |
| 跳过原因细分，`no_context` 单列 | 1.1 节 | 状态与统计能直接区分真跳过与不合格请求 |
| 状态里记录分项计时与客户端计数 | 重构前的分析建议先加时间线记录 | 真机上可直接看到排队、计算、等待与客户端超时 |

打分口径与旧核心逐题一致：留出集 1293 题，同一个模型文件，首选一致 1293/1293，完整排序一致 1293/1293，分数最大差 0.0000（实测）。

## 4. 舍弃的做法

| 做法 | 理由 |
|---|---|
| 异步加载线程、共享互斥锁、挂起请求槽位、生命周期读写锁 | 单一所有者的工作线程使它们都不再需要 |
| 回退 Qwen | 只服务 Suzu。没有词表或模型时返回 `no_model`，输入不受影响 |
| 上文窗口的滞后滑动（上文超过 30 字后先截到 20 字再追加） | 能减少窗口滑动时的整段重解，但会改变模型输入，与旧核心不再逐题一致。上屏后到第一次打分（第 3 个字母）之间通常有 300 ms 以上，整段重解（2 线程约 15 ms）来得及，收益不足以抵消准确率风险 |
| 自写前向引擎 | 共享 KV 之后，一次打分的计算约 6 ms（4 线程），剩下的主要是矩阵运算本身。自写引擎成本大、收益不确定，暂不做 |
| 默认打开 CPU 权重重排、改用 Q4 量化 | 旧测量显示手机上收益有限且内存变大，Q4_0 准确率降到 99.1%。重排保留为可选项（`use_repack`、`--repack`） |
| Android 进程内推理 | Android 采用守护进程方案。Engine 不依赖 Lua 与网络，以后切换只需让客户端直接链接 `runtime/` |
| 请求编号 | 守护进程保证按时应答，不会有迟到的应答 |

## 5. 与旧核心的行为差异

- `score(ctx, cands, false)` 在上文未预解码时不再跳过，而是在时限内现场解码；时限内算不完返回 `nil, "timeout"`。
- 上文不足 2 个字时返回 `nil, "no_context"`（旧核心只返回 `nil`）。
- 状态文件 `skipped` 的含义变为“真正的跳过”，新增 `skip_timeout`、`no_context`、`engine`、`client` 字段；旧字段保留，`skip_unprepared`、`skip_busy` 恒为 0。
- 未设置 `student_vocab` 时按模型文件名找同名词表；找不到就不加载。
- 线程数上限为核数减一。
- 守护进程常驻内存由约 118 MB 降到约 63 MB（Linux 主机构建，实测）。

| 项目 | 方法 |
