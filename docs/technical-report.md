# 技术报告：实测结果与未验证项目

本文收录 suzu-ime 的全部实测数据：各平台的延迟与内存、候选生成的对照、新旧核心的一致性，以及尚未验证的项目。概览与快速开始见仓库根目录的 [README](../README.md)。下文的候选生成对照与延迟数据由 Suzu-2.1 测得，Suzu-2.4 的数字见 [模型卡](https://huggingface.co/IzumiThe3rd/Suzu-2.4)，推理核心的设计与测量见 [design/](design/README.md)。

## 实测结果

以下数据除“默认配置的当前数据”一节外，均为 2026-10-19 测得（当时只有重排，没有候选生成与统一排序）。延迟来自按键仿真 `tests/keysim.lua`：用模拟的 Rime 环境驱动真实的 Lua 脚本与核心，按 100～300 ms 的间隔输入 100 个词，含快速连按、退格、换行和四字词。“按键最坏”是一次按键在输入法线程上花掉的最长时间。新旧核心使用同一个模型文件（Suzu-2.1 Q8_0）。

### 默认配置的当前数据

2026-10-20 到 21 日，默认配置（统一排序、候选生成开启、Lua 个人词对）下的按键仿真，100 个词，Suzu-2.1 与 Suzu-2.4 的延迟没有可见差别。范围取自各平台的多轮运行：

| 平台 | 条件 | 打分 p99 | 每次按键 p99 | 每次按键最大 | 常驻内存 |
|---|---|---|---|---|---|
| macOS | 4 线程，每层 20 个首字，两个模型各两轮 | 10.2 到 12.4 ms | 21.3 到 23.0 ms | 27.7 到 52.0 ms | 约 118 MB（每层 10 个首字约 112 MB；不含候选生成约 66 到 72 MB） |
| Windows | 4 线程，两轮，有无基础词对表各一次 | 6.2 到 19.0 ms | 22.4 到 23.0 ms | 24.7 到 28.1 ms | 待测 |
| Android | 经 adb，2 线程，每层 10 个首字，两轮 | 17.2 到 37.4 ms | 34.8 到 39.4 ms | 49.0 到 55.2 ms | 约 81 MB |

读表须知：

- 每次按键的耗时包含 Lua 与核心在输入法线程上的全部时间，p99 是 99% 的按键在此时间内完成，最大值是单次最坏，两者不能混着比。
- 默认配置下每次按键 p99 约 22 ms，是候选生成和统一排序带来的，下一节旧配置的数字（10 月 19 日，只有重排，没有候选生成）约 10 到 12 ms，两节的条件不同。
- Android 的数字经 adb 转发，不含手机上 Lua 的真实耗时；同一配置另一次测量的每次按键 p99 为 64.2 ms，波动较大。
- 开启候选生成后 Mac 的常驻内存比不开多约 46 到 53 MB（词典索引与束搜索的缓冲），比手机上多得多，原因未查清，列入待办。

### 旧配置的汇总（2026-10-19，只有重排）

各平台新核心的汇总如下。常驻内存指加载模型并稳态打分后的进程驻留集（Linux 与 Mac 的 RSS，Windows 的工作集），含被映射的模型文件页（约 44 MB）；Android 为守护进程自己的 RSS。各平台的测量条件见下文。

| 平台 | 打分中位数 | 打分 p99 | 按键最坏 | 常驻内存 |
|---|---|---|---|---|
| macOS（进程内，4 线程） | 3.8 ms | 9.1 ms | 11.9 ms | 71.8 MB（旧核心 132 MB） |
| Windows（进程内，4 线程） | 2.7 ms | 4.7 ms | 9.1～9.7 ms | 69.5 MB（旧核心未测） |
| Android（守护进程，2 线程） | 11.2 ms | 19.3 ms | 36.8 ms | 约 61 MB（旧核心 112～116 MB） |

### macOS

Apple Silicon Mac，4 线程，新旧核心用同一段仿真脚本：

| 指标 | 旧核心 | 新核心 |
|---|---|---|
| 打分中位数 | 6.2 ms | 3.8 ms |
| 打分 p99 | 12.0 ms | 9.1 ms |
| 打分最大 | 13.0 ms | 9.5 ms |
| 第二阶段最大 | 40.3 ms | 11.3 ms |
| 按键最坏 | 40.4 ms | 11.9 ms |
| 跳过 | 0 | 0 |

全部测试（含守护进程的破坏性测试）在 Mac 上 25 秒通过。验收要求 macOS 打分 p99 不超过 20 ms，实测 9.1 ms。

### Android

Zenfone 10，守护进程 2 线程。守护进程常驻内存约 61 MB，旧版约 112～116 MB，上限要求为 120 MB。按键仿真经 adb 端口转发连接手机上的守护进程，数字含转发开销：

| 条件 | 打分中位数 | p99 | 最大 | 按键最坏 | 跳过 |
|---|---|---|---|---|---|
| 正常速度 | 11.2 ms | 19.3 ms | 21.2 ms | 36.8 ms | 0/180 |
| 快速输入（间隔减半） | 11.8 ms | 17.1 ms | 18.3 ms | 31.1 ms | 0/180 |

验收要求手机打分 p99 不超过 50 ms、最大不超过 100 ms，跳过率不超过 2%。安装后约 17 分钟的使用中，核心收到 781 个打分请求：619 个拿到结果，2 个跳过（超时 1 个、手动关闭 1 个），159 个上文不足 2 个字，客户端等待最长 26 ms。这段计数含测试流量，只作参考。

`tests/test_daemon.py` 的手机模式 34 项全部通过。破坏性测试（杀进程、冻结、删除模型）只在电脑上做过，没有在手机上做。

旧版状态里约 19% 的“跳过”，大部分是上文不足 2 个字的请求。这类请求核心本来就不打分，上面的 159/781 约为 20%，与之相符。新版把它们单列为 `no_context`，不再计入跳过。

### Windows

Windows 11，MSVC 14.44，4 线程，机器空闲，120 个词，新旧交替各 2 轮：

| 指标 | 旧核心 | 新核心 |
|---|---|---|
| 打分中位数 | 6.0 ms | 2.7 ms |
| 打分 p99 | 7.4～7.6 ms | 4.7 ms |
| 打分最大 | 10.0 ms | 5.1 ms |
| 按键最坏 | 12.1～13.9 ms | 9.1～9.7 ms |
| 跳过 | 0% | 0% |

Windows 已切换到与 Mac、手机共用的 `ai_rerank_*` Lua，光标上文用 UIA 或 COM 读取（接入层是与 Mac、手机共用的 `rime/lua/ai_rerank_app_ctx.lua`），旧的 `llm_filter.lua` 路径保留为回退，部署与回滚脚本见 `windows/deploy_airerank.ps1`。上表为切换前的数据，切换后候选生成开启时的按键延迟见“候选生成”一节的表。空闲卸载后，进程私有内存由 45 MB 降到 3 MB，工作集由 69.5 MB 降到 11.0 MB。

部署脚本 `windows/deploy_core.ps1` 约 4 秒完成替换，回滚演练 1 秒生效，过程中不弹窗。验证中发现并修复了两个问题：

- 光标上文快照在每次上屏、编辑键或点击之后约 2.5～4 秒内无效，这段时间开始打字时拿不到上文。修复后，打字前等待 1.0、2.6、5.0 秒三种情况都正常重排。
- Lua 脚本里 4 处用 `os.rename` 覆盖已有文件，Windows 上会失败，导致个人词对文件压缩与日志轮换不生效。现已改为：改名失败时先删除目标文件，再改名。

### 候选生成

Mac 上用真实 librime 加完整配置逐键输入（统一排序，名次先验系数 0.05），题目取自留出集，上文干净。两字母简拼 407 题，混合输入（首音节全拼加其余声母）291 题，均为抽样。“旧排序”指 2026-10-20 之前的配置：Mac 的触发条件是 3 个字母起，所以两字母简拼不重排，等于关 AI；手机从 2 个字母起重排，表中单列“手机配置”（最多 9 个候选，门控 0.5，简拼门控 1.5）。

| 输入 | 做法 | 首选 | 答案进前 5 名 |
|---|---|---|---|
| 两字母简拼 | 关 AI（Rime 原顺序，也是此前 Mac 的实际行为） | 10.7% | 32.8% |
| | 旧排序，手机配置（2 个字母起重排） | 23.8% | 37.6% |
| | 统一排序，不生成 | 25.8% | 41.3% |
| | 统一排序，取前 40 个候选再排序（已删除的方案，名次先验 0.25 时测得） | 32.9% | 65.8% |
| | 统一排序加生成，每层展开 10 个首字（手机） | 41.3% | 71.5% |
| | 统一排序加生成，每层展开 20 个首字（桌面） | 41.8% | 73.7% |
| 混合输入 | 关 AI（Rime 原顺序） | 33.0% | 61.2% |
| | 旧排序（此前 Mac 与手机的配置） | 62.9% | 79.4% |
| | 统一排序，不生成 | 61.2% | 76.3% |
| | 统一排序加生成，每层展开 10 个首字（手机） | 68.4% | 93.8% |
| | 统一排序加生成，每层展开 20 个首字（桌面） | 68.7% | 94.2% |

相对此前的配置，Mac 的两字母简拼首选由 10.7% 升到 41.8%，混合输入由 62.9% 升到 68.7%；对手机的旧配置，两字母简拼由 23.8% 升到 41.3%（每层 10 个首字）。全拼输入不受影响（首选 91.7%，与旧排序 91.2% 相当）。名次先验系数取 0.05，是因为 0.25 时两字母简拼首选只有 35.4%，0 时为 42.8%；先验主要在上文完全错误时才有约 3 个点的保护。

延迟与内存：

| 平台 | 条件 | 结果 |
|---|---|---|
| macOS | 按键仿真，4 线程，每层 20 个首字 | 打分中位 4.0 ms 对 4.5 ms（生成关闭对开启），p99 9.6 对 11.0 ms，按键最坏 21.2 对 17.6 ms，无超过 50 ms 的按键 |
| Android | 按键仿真经 adb 转发，2 线程，每层 10 个首字 | 跳过 0.54%，打分中位 11.1 ms、p99 37.2 ms，按键 p99 64.2 ms、最坏 86.2 ms，超过 50 ms 的按键 14/956（关闭时约 3/954）；守护进程常驻内存约 61 MB 升到约 80 MB |
| Windows | 按键仿真，4 线程，候选生成开启，Suzu-2.1，有无基础词对表各两轮 | 每次按键 p99 22.4 到 23.0 ms、最大 24.7 到 28.1 ms，打分 p99 6.2 到 19.0 ms，跳过 0，无超过 50 ms 的按键；准确率与内存待测 |

题目的答案取自留出集，含不少冷门词，真实简拼多打常用词，实际收益待回放数据。手机的数字含 adb 转发开销，是上界。词典索引共 36.7 万词，主机上加载约 0.5 秒，在模型就绪后的单独线程里进行，不阻塞打分。

### 准确率与内存

新旧核心使用同一个模型时，打分逐题一致：Linux 与 Mac 上 1293 题留出集首选一致 1293/1293，分数最大差 0.0000；Windows 上 1325 题首选一致率 100%。首选准确率不变（1293 题上均为 92.42%）。

内存的测量方法：在测试解释器进程里加载 `rime_llm`，模型为 Suzu-2.1 Q8_0（43.9 MB），连续打分 300 次，读进程内存计数。2 线程与 4 线程没有可见差别，稳态不增长。

| 平台 | 口径 | 模型未加载 | 稳态 | 空闲卸载后 |
|---|---|---|---|---|
| macOS | RSS | 10.4 MB | 71.8 MB | 未测 |
| macOS | footprint（脏页） | 2.6 MB | 20 MB | 未测 |
| macOS，旧核心 | RSS／footprint | 10.3 MB | 132 MB／81 MB | 无此功能 |
| Windows | 工作集 | 8.5 MB | 69.5 MB | 11.0 MB |
| Windows | 私有页 | 2.0 MB | 19.9 MB | 3.2 MB |
| Linux 主机，守护进程 | RSS | 未测 | 63.4 MB（旧核心 118.7 MB） | 无 |
| Linux 主机，进程内 | RSS | 未测 | 67 MB（旧核心 127 MB） | 11 MB |

模型带来的增量在 Mac 与 Windows 上都约为 61 MB 的 RSS 或工作集，其中约 44 MB 是被映射的模型文件页，匿名内存约 18 MB。小狼毫进程本身另有 Rime 与词库，Windows 还会修剪空闲进程的工作集，实际进程的读数不能归因于核心。

新旧核心在模拟手机速度（解码拉长 2.5 倍）下的对照、各项优化的分项效果与故障注入结果，见 [docs/design/core-measurements.md](docs/design/core-measurements.md)。

## 未验证的项目

- 候选生成在 Windows 上的效果（准确率）与内存：待测；按键延迟已测，见“候选生成”一节。
- 手机上统一排序与候选生成长期使用时的按键卡顿：按键仿真里超过 50 ms 的按键占 1.5%，真实使用中的比例待测。
- 统一排序的参数（名次先验系数 0.05 等）在真实输入下是否合适：待回放数据，攒到约 2000 条后用 `tools/replay.py` 校准。
- 输入事件流在手机上的盲区（点按改字看不到）：Trime 补丁尚未处理，影响覆盖率，待评估。
- 手机息屏后的行为与耗电：待测。
- 长期真实使用中，真正跳过与 `no_context` 各占多少：依据是 `ai_status.json` 的 `engine` 与 `client` 字段，待数据。
- Windows 上除 Edge 以外的应用（记事本、聊天软件）里的光标上文与重排：待测。
- 手机重启后，守护进程仍须经 adb 或 Shizuku 启动，尚无开机自启的办法。
